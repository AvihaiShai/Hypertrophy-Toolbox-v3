## 1. The question this plan answers

The owner asked two things:

1. Should the project move to Docker images for easier management, deployment and CI/CD, or is there a better alternative?
2. Is the code "spaghetti" that needs a deep refactor?

Both reviewers independently reached the same top-line answer and converged on the
ordering below over four review rounds.

## 2. Agreed answers (both reviewers, no open dispute)

| # | Decision | Rationale (short) |
|---|---|---|
| A1 | **No Docker for the product.** Deferred until a second machine, a server/NAS deployment, or remote (phone) access becomes a product goal. | Product is single-user and local-first. Source checkouts run via `START.bat` (venv Python + `app.py`); the frozen Windows exe is built by `_packaged-windows.yml` and run via `app_launcher.py`. Docker would add Docker Desktop and a WSL2 backend for this user, and the CI pain that exists (Windows vs Linux pytest collection, per-platform visual baselines, the Windows exe build) is not something a Linux container addresses. `HT_RUNTIME_DIR` already makes a container volume configurable, so a Dockerfile stays cheap to add later. |
| A2 | **No deep refactor / rewrite.** | Layering is intact: zero `routes→routes` imports, zero `utils→routes` imports; 13 blueprints; one DB handler; standard response and logging helpers; 52k lines of pytest. Bounded hotspots exist (§3.4) and are addressed as targeted extractions. |
| A3 | **Process and documentation weight is a substantial, measured cost and is addressed first in a bounded way.** | §3 shows the size of the active reading surface. Whether it *caused* the feature slowdown is an unmeasured hypothesis, not a finding. The plan acts on the measured cost without depending on the causal claim, and caps the first docs change (WS1) so it cannot become a prerequisite for code work. |
| A4 | **Docs trimming is file-level and dependency-aware, never folder-wholesale.** | CI reads `docs/ci_cd_phase3/pyright-baseline.json`, `docs/CSS_PHASE4_WP4_1_STYLELINT_BASELINE.json`, `docs/test_inventory/TEST_INVENTORY.json`; eight scripts under `scripts/` reference `docs/` paths; #514 identified live records inside `testing_phase3`, `toast_action_continuity`, `backup_confirmation_continuity` and current design references inside `user_profile`. The retention age rule was already replaced by #515. |
| A5 | **The diff-stage gate is already lean; the overhead is at plan stage and in post-merge bookkeeping.** | The change-type table requires one pytest target + `code-reviewer` for routes, and for frontend changes **no reviewer** (tests are still required: matching Chromium specs, visual matrix, Stylelint). | A6 | **An application factory is the next code candidate**, after the WS3 design items in §4 are completed and the owner answers Q8. | It removes import-time side effects in `app.py` (database migrate/seed/initialize/backup **and** logging handler creation), deletes the duplicated 13-blueprint registration and re-declared `/erase-data` in `tests/conftest.py`, and removes the "register in both places" footgun from `CLAUDE.md` §4A. | A9 | **Interleave, do not serialize.** One small completed docs slice → factory (once designed and approved) → focused extraction. Broad archiving and WS2 are not prerequisites for code work; approved code work uses the existing gates. | Both reviewers, round 3–4. |

### WS3 — Application factory (design must be complete before approval)
**Goal.** `import app` performs no filesystem or database work; production, launcher and tests build the app through one path.
**Design items to complete before §6 approval.**
- Inventory every import and launch caller: `app.py __main__`, `app_launcher.py`, `Hypertrophy-Toolbox.spec` / packaged bootloader, `tests/conftest.py`, and the four import-dependent tests `test_catalog_seed_bootstrap.py`, `test_real_app_db_isolation.py`, `test_static_cache_policy.py`, `test_pattern_coverage.py`.
- Define `DB_FILE` / `HT_RUNTIME_DIR` precedence and where process-global DB configuration (`utils.config.DB_FILE`) is set.
- Define the empty test-schema path (unseeded on purpose) versus the real `init_runtime()` path.
- Include logging transitively: `app.py:72` calls `setup_logging(app)`, **and** 45 `routes/` and `utils/` modules call `get_logger()` at module level, which lazily runs `setup_logging()` (`utils/logger.py:123-127`) and creates the log directory and file handler on first import of almost any module. Either logging configuration becomes explicit and idempotent (safe under repeated factory calls and under tests), or the "no side effects" promise is narrowed in writing to the database and the logging side effect is documented as retained.
- Specify, in writing, the initialization order among configuration (`DB_FILE` / `HT_RUNTIME_DIR` / port), logging, `create_app()` and `init_runtime()`; what a second `create_app()` call in one process does (new app, shared logger, no re-migration); and which of these the packaged bootloader and `app_launcher.py` perform. WS3 is not approvable until these three paragraphs exist.
- Cover all 13 blueprint registrations, error handlers / fallback handlers, template filters, static cache policy, and the real `/erase-data` confirmation + backup contract.
**Shape.** `create_app(config)` registers blueprints, handlers, filters and `/erase-data`. `init_runtime()` performs, in the existing order: `prepare_runtime_database()` → `bootstrap_runtime_database()` → `run_all_initializers(force_base=False)` → `upgrade_catalog_from_seed()` (skipped on fresh seed) → `create_startup_backup()` (skipped on fresh seed). Only the two launch paths call it. Remove the "register in both" line from `CLAUDE.md` §4A.
**Acceptance.** `/verify-suite` (full pytest + Chromium); packaged-Windows smoke; fresh-process import and runtime checks on scratch paths covering first install, existing-DB upgrade, backup/restore, and both launch paths; a test asserting the startup call order; server behavior unchanged (no Waitress in this PR).
**Gates.** Route/API + DB rows → `code-reviewer` + `architecture-reviewer`, plus whatever the actual diff's path union adds.
**Parallel with recovery:** read-only design work can proceed now. Implementation and runtime checks remain subject to the written design answers, Q8(a)'s applicable sequencing decision and the workstream's approval; use isolated runtime paths under the conditions above.
