# Repository Decisions

This document records durable, cross-cutting project decisions as lightweight
architecture decision records (ADRs). Accepted decisions remain here as
historical context even when the code or tool that prompted them is later
retired; changed decisions are superseded by a new ADR rather than silently
rewritten.

## Historical exercise-import rules

The Excel-to-SQLite merge utility that these rules governed is no longer present
under `scripts/`. The rules are retained as historical context for ADR-001, not
as instructions for a currently supported command.

- **Normalization rules**: Trim leading/trailing whitespace, collapse internal whitespace to a single space, and normalize endash/emdash characters to the ASCII hyphen before any comparisons.
- **Exact name matching**: Import logic only merges rows whose normalized `exercise_name` strings are identical. No fuzzy, partial, or substring matching is permitted.
- **Empty cell handling**: Blank strings and missing values coming from Excel are treated as nulls and never overwrite populated database fields.
- **Case sensitivity flag**: `--nocase` enforces a `COLLATE NOCASE` uniqueness constraint; when omitted, uniqueness is strictly case-sensitive.
- **Update-only flag**: `--update-only` converts unmatched Excel rows into skipped entries instead of inserts.
- **Default paths**: Unless overridden, the tool reads from `data/exercises.xlsx`, writes to `data/database.db`, and emits Markdown artifacts in `docs/`.

### Data semantics

- Equipment semantics: The equipment field intentionally includes both gear (Barbell, Dumbbells, …) and categories (Yoga, Recovery, Stretches, Cardio). These are first-class filter values.
- Enumerations: Incoming `force`, `mechanic`, and `difficulty` values are canonicalized to `Push`/`Pull`/`Hold`, `Compound`/`Isolation`, and `Beginner`/`Intermediate`/`Advanced` respectively before merging.

## ADR Log

New cross-cutting or durable project decisions should be added here as lightweight ADRs. Use the next sequential number, keep the original ADR unchanged after acceptance, and supersede it with a new ADR if the decision changes.

### ADR-001: Exercise import uses exact normalized name matching
- **Date**: 2026-05-11
- **Status**: accepted
- **Context**: The exercise import utility merges external Excel rows into the local SQLite exercise table. Fuzzy or partial matching could accidentally merge distinct movements and corrupt the exercise catalog.
- **Decision**: Import matching is based only on identical normalized `exercise_name` strings. Empty Excel cells never overwrite populated database values, and `--update-only` skips unmatched rows instead of inserting them.
- **Consequences**: Imports are predictable and auditable, but users must clean source exercise names before import when they expect two rows to match.

### ADR-002: The repository root holds five categories of file, and nothing else
- **Date**: 2026-07-26
- **Status**: accepted
- **Context**: The root-cleanup audit began from the impression that nearly every root file other than `app.py`, `CLAUDE.md`, `README.md`, and `requirements.txt` was accumulated clutter. Inspection did not support that. Most root files are there because a tool discovers them from the project root, and moving them would require wrapper commands or path overrides and make the project less conventional. The real problems the audit found were elsewhere — a tracked user database and unrestricted packaging inputs — and are addressed by `docs/rootdircleanup.md` Packets A and B. What the root actually lacked was a stated rule, so that the next judgment call is answerable without re-running the audit.
- **Decision**: The repository root may contain exactly these categories:

  | Category | Current members |
  |---|---|
  | Application entry points | `app.py`, `app_launcher.py` |
  | User-facing start / readme files | `README.md`, `QUICK_START.md`, `START.bat`, `RUN_APP.bat` |
  | Build manifests | `Hypertrophy-Toolbox.spec`, `build_exe.bat`, `requirements.txt`, `requirements-build.txt`, `package.json`, `package-lock.json` |
  | Tool configuration that relies on root discovery | `.gitignore`, `.mcp.json`, `.python-version`, `pyproject.toml`, `pyrightconfig.json`, `pytest.ini`, `.stylelintrc.json`, `.stylelintignore`, `tsconfig.json`, `vitest.config.js`, `playwright.config.ts` |
  | Repository operating instructions | `CLAUDE.md`, `AGENTS.md` |

  Generated reports, screenshots, scratch databases, baselines, and personal state do not belong in the root. They go under the gitignored `artifacts/` (build output under `build/` and `dist/`; runtime state under the path `utils/runtime_paths.py` resolves).

  Two corollaries, both learned the hard way:
  - **Do not move a root file merely to reduce the file count.** Some are load-bearing at the root: `Hypertrophy-Toolbox.spec` derives `REPO_ROOT` from `SPECPATH`, and a packaging contract test asserts `build_exe.bat` invokes it by that exact name. Root visibility is also part of what makes `START.bat` usable for its audience.
  - **A file in an approved category is not automatically justified.** It still has to be correct and non-duplicative; C2 trimmed `QUICK_START.md` rather than deleting it.
- **Consequences**: Adding a root file now requires naming its category, which makes the review question concrete instead of aesthetic. New generated output has an obvious destination, so the "temporary file at the root" habit has no excuse. The cost is that this table needs updating whenever a genuinely new root file is added — accepted, because the alternative is re-deriving the policy from scratch each time. The audit behind it is recorded in `docs/rootdircleanup.md` §8.4 and §12.

### ADR-003: Python 3.14.6 is the minimum supported runtime
- **Date**: 2026-07-29
- **Status**: accepted
- **Context**: The repository advertised Python 3.11+ while development and executable builds already ran on 3.14. CI and Pyright therefore validated an older runtime than the one used to ship the application, and local environments could silently retain an obsolete interpreter.
- **Decision**: Python 3.14.6 is the minimum for source runs, tests, CI, and executable builds. `.python-version` is the exact CI/environment-manager pin; Pyright targets the corresponding 3.14 language and standard-library surface; `utils/python_version.py` enforces the patch-level floor; and both Windows entry points derive the registered Python minor from the pin, validate its patch level, and validate any retained `venv`.
- **Consequences**: The project no longer promises Python 3.11–3.13 compatibility. Runtime, CI, analysis, and packaging now agree, and stale virtual environments fail with an actionable message. Adopting a newer minimum requires updating the canonical pin, runtime contract, Pyright target when the minor changes, its committed diagnostic baseline, and verification under the exact interpreter.

### ADR-004: The browser matrix is Chromium-only
- **Date**: 2026-08-02
- **Status**: accepted
- **Context**: `playwright.config.ts` declares exactly one project, `chromium`, and every CI invocation passes `--project=chromium`. Nothing had ever *decided* that — it was the Playwright scaffold default that no one revisited, so cross-browser coverage was absent by inertia rather than by choice. That left a standing implicit question ("shouldn't we add Firefox and WebKit?") that resurfaced in each testing review and could not be answered from the repository. The product context bounds it: this is a single-user, local-first tool served from `127.0.0.1:5000` and launched by its owner on Windows through `START.bat` / the packaged executable. There is no deployed multi-user surface and no analytics-derived browser distribution to serve. A matrix would multiply E2E wall-clock and, more importantly, multiply the visual-baseline set — already 84 committed Linux PNGs plus a Windows set, per renderer — and every added renderer needs its own baseline generation and human pixel review.
- **Decision**: Chromium is the only supported browser for the automated test suite, and the browser matrix is closed. Do not add Firefox or WebKit projects to `playwright.config.ts`, and do not add browser dimensions to the CI matrix, without superseding this ADR. This records the *testing* scope only; it makes no claim that the application is incompatible with other browsers, and it does not license Chromium-only code (vendor-prefixed CSS, Chrome-specific APIs) in the application itself.
- **Consequences**: E2E cost and visual-baseline maintenance stay bounded to one renderer, which is what makes per-platform pixel baselines affordable at all. The suite cannot catch a Firefox- or WebKit-specific rendering or API regression; if the owner ever opens the app in another browser, that is unverified territory and belongs to the manual layer. Reopening this is a real decision with a real bill — a new baseline set per renderer, generated on a pinned image and reviewed by a human — so it should be driven by an actual observed defect or a genuine distribution change, not by matrix-completeness instinct. Recorded per decision **D5** of [`TESTING_STRATEGY_PLANNING.md`](TESTING_STRATEGY_PLANNING.md) §6, signed 2026-08-02.

### ADR-005: E2E performance work is directed by measurement, not by count
- **Date**: 2026-08-08
- **Status**: accepted
- **Context**: Two E2E cleanups were queued on the strength of how many items they contained rather than what those items cost. The hard-wait inventory reports 92 `waitForTimeout` calls across 15 files, and `api-integration.spec.ts` holds 57 tests — the two largest counts in the suite, and so the two obvious targets. Instrumenting the suite first (`scripts/playwright_timing_report.py`) contradicted both. Across the local functional group (29 specs / 508 tests / 718.4s), `api-integration.spec.ts` costs **2.3s — 0.3%** of the suite, because its tests are HTTP calls with no browser navigation. The 92 hard waits total **61.3s of literal delay, ~8.5%**, and their distribution does not follow duration: the slowest file, `ui-hardening.spec.ts` at 74.5s, contains exactly one 50ms wait, while the heaviest wait-debt file, `volume-splitter.spec.ts` at 23 calls, is mid-pack at 38.3s. Sharding, which no count would have nominated, governs the rest: the required CI set measures 678.9s locally against a 74.5s slowest-file floor, so file granularity does not bind until roughly N=9.
- **Decision**: E2E performance changes require timing evidence for the specific change, produced from the group that the decision applies to — the required CI functional set for CI shard decisions, never the larger local group. Specifically: `api-integration.spec.ts` is **not** split, moved, or trimmed for performance, and the blanket 92-wait rewrite is **not** run as a performance change. A hard wait may be replaced only when profiling identifies that wait as material to a genuinely slow test and an observable condition is available; hard waits are never removed mechanically, and the inventory's accepted count is never weakened to make a number look better. Determinism work on hard waits remains valid on its own reliability grounds and belongs to a separate workstream with its own justification.
- **Consequences**: Effort follows cost rather than inventory size, and two large, risk-bearing refactors of working test code are not undertaken for a combined ceiling under 9% — of which the API split's share is 0.3%. The cost is that hard-wait determinism debt stays on the books, tracked but unpaid, and that any future claim about E2E speed now needs a measurement attached. `api-integration.spec.ts` retains cross-process, real-server coverage that pytest's in-process client cannot reproduce, which is the coverage a split would have put at risk for no measurable gain.

### ADR-006: Local Playwright sharding is N=1 only; same-machine N>1 is rejected
- **Date**: 2026-08-08
- **Status**: accepted
- **Context**: `scripts/run-playwright-shards.ps1` was built to reproduce CI's 2-way split locally — each shard its own process, port, SQLite file, and artifacts root, so nothing is shared and the within-shard serial ordering the specs rely on is untouched. N=1 measured 477/477 in 719.0s and is reliable. Every N>1 configuration failed, and the failures scaled with N. The first matrix (N=2 476/477, N=3 468/477, N=4 449/477) was invalid as evidence because each configuration inherited the previous one's `TIME_WAIT` backlog, so its timings cannot be used to select a shard count. A controlled re-run settled it: after a gate that waited 120.8s for a measured clean start (leftovers 0, busy candidate ports 0, `TIME_WAIT` on candidate ports 0, total `TIME_WAIT` 29), N=2 still **failed 4/477** with both shards exiting 1, in 407.2s.

  The cause is machine-wide and cannot be partitioned by per-shard ports, databases, or artifact roots. Werkzeug's `WSGIRequestHandler` speaks HTTP/1.0 and closes the connection per request, so **every** request consumes an ephemeral port for the full 120-second recycle interval. About 89.9% of the suite's requests are static assets (30,752 of 34,253), and a fresh Playwright browser context re-fetches the page's whole asset set on each navigation (68 same-origin requests on `/workout_plan`), so the suite's port consumption is dominated by asset traffic rather than by test logic. N=1 averaged ~57 connections/s and a steady state of ~6,840 ports. N=2 averaged ~85 connections/s and peaked at 16,318 of the 16,384-port dynamic range (99.6%). Sharding compresses the same total connection volume into less wall-clock, so it raises the connection *rate* against a fixed pool — which predicts N=1 clean, N=2 marginal, N=3/N=4 worse, exactly the observed ordering. CPU, processor queue, memory, and disk were measured and were not limiting.

  Three failure signatures were recorded and are deliberately kept separate: a client-side `net::ERR_ADDRESS_IN_USE` on `page.goto` (`nav-dropdown.spec.ts:143`, shard 1, port 5300, t≈198s, 15,263/16,384 ports, 15,219 in `TIME_WAIT`); two 30-second timeouts (`summary-pages.spec.ts:388`, `workout-log.spec.ts:222`, both t≈292s, ≈16,301 ports); and one other assertion failure (`volume-progress.spec.ts:319`, t≈213.8s, 16,318 ports). There were **zero bind failures within ±60s of either timeout in the same shard**, so the timeouts and the bind failure must not be claimed as one directly correlated event. All four specs passed in isolation after a full drain (nav-dropdown 7/7, summary-pages 20/20, volume-progress 16/16, workout-log 23/23), so no individual spec regression was demonstrated.

  Every lever that would make N>1 work is out of bounds or worse than the problem: OS/TCP/registry/dynamic-port/`TIME_WAIT` tuning makes the result a property of one machine's configuration rather than of the repository; HTTP/1.1 keep-alive (even behind a test flag) and asset cache-policy changes alter what the suite exercises relative to production; a different WSGI server adds a dependency to serve a benchmark; and retries, timeout inflation, shared browser contexts, or reduced coverage would buy the number by weakening the gate.
- **Decision**: **N=1 is the only supported local Playwright configuration.** `scripts/run-playwright-shards.ps1` defaults to `-Shards 1`, and N>1 warns at runtime that it is an unsupported diagnostic. The launcher and all N>1 evidence are retained so the measurement stays reproducible, but a green N>1 run is not evidence and must not be used to select a shard count or to claim a local speedup. Reopening this requires a new owner decision that names which forbidden lever is being bought and why.

  **This says nothing about CI.** CI's `e2e-functional-shard` matrix runs each leg on its own runner with its own port pool, server, and freshly seeded database, so it shares none of the machine state implicated here. Its N=2 design remains valid and is unchanged by this ADR.
- **Consequences**: The local E2E fast lane is 719.0s and stays there; local wall-clock improvement has to come from making the work smaller rather than from running it in parallel, which is what the profiling in [`E2E_PERFORMANCE_PROFILE.md`](E2E_PERFORMANCE_PROFILE.md) is for. The diagnosis also has standing value beyond sharding: the same HTTP/1.0 connection-close behavior is why per-navigation readiness is expensive, so anything that multiplies navigations on this machine pays for it. The cost is that the launcher keeps a parameter whose interesting values are unsupported; the runtime warning and this ADR are what stop that from being rediscovered as a bug.

### ADR-008: `BACKUP_SCHEMA_VERSION` is a reserved informational label, not an enforced contract
- **Date**: 2026-08-14
- **Status**: accepted
- **Context**: `utils/program_backup.py` defines `BACKUP_SCHEMA_VERSION = 1`, persists it to `program_backups.schema_version`, and returns it from four `/api/backups` endpoints, where the Backup Center displays it as a "Schema" stat. Nothing reads it to make a decision: `restore_backup()` selects only `id`, `name`, and `item_count`, and structural compatibility is handled by `_check_column_exists()` probing the destination columns on `user_selection` at restore time. A TODO at the definition site claimed the first consumer "should read it in `restore_backup` to trigger field migration", which left the field looking like pending work and made it Testing Strategy decision **D6**, whose written recommendation was to define and enforce a compatibility policy.

  Tracing the field settled it the other way. The label had already failed to track a real payload change: it shipped in `720cb0e` (2026-02-03), and `6b99535` (2026-02-05) added `superset_group` to `program_backup_items` with an `ALTER` migration but **without** bumping it. `create_backup()` also writes `exercise_order` / `superset_group` as `NULL` when the source columns are absent, so rows labelled version `1` already span at least three column populations. Version 1 has never identified a payload shape.

  Two further facts bound the value of enforcement. Backups are database rows with **no import path**, so a foreign version can reach `restore_backup()` only if a future build writes one and the user then reverts to an older build — meaning a guard shipped today protects only builds ≥ today against versions written by builds > today. And the guard would sit on the disaster-recovery path, where a false refusal is worse than the silent mis-restore it prevents. Removal was also considered and rejected: it is a breaking response-contract change for an unread integer, and a hard column drop is not revert-able, because the reverted code's `INSERT` would name a column the user's database no longer has.
- **Decision**: `BACKUP_SCHEMA_VERSION` is retained as a **reserved informational label**. `restore_backup()` stays **deliberately version-blind**, structural compatibility remains owned by destination-column probing, and the column, the four API fields, and the UI tile all stay exactly as they are. No supported range, no guard, no error code. **Changing the `program_backup_items` payload shape requires all three of**: bumping the constant, adding an `ALTER`-based migration in `initialize_backup_tables()`, and adding the matching branch in `restore_backup()` — doing one or two of the three is what made the label meaningless the first time. This supersedes the recommendation of A recorded in `TESTING_STRATEGY_PLANNING.md` §6; the reasoning is in §8.1b and the requirements brief is [`backup_schema_version/PLANNING.md`](backup_schema_version/PLANNING.md).
- **Consequences**: The question stops being re-derived — the contract is stated where the constant is defined, so the next reader does not reopen it. Phase 3 step 11's precondition is discharged and its fuzz target is fixed as the `program_backup_items` rows rather than the version. Three tests now hold the contract: version-blindness is pinned, so an accidental future guard fails; the persisted value is asserted against a patched constant, because a plain persisted assertion is satisfied by the column's own `NOT NULL DEFAULT 1` — measured, not assumed; and the field's presence in all four responses that carry it is pinned, so a later silent removal fails first. What is knowingly accepted is that a future v2 payload read by a build predating the bump would be restored without a guard; the only route into that state is an app downgrade on the same machine, and the bump-and-branch rule is what keeps it from arising.

### ADR-009: A muscle in two P/S/T roles is credited the sum of those role weights, and `get_rep_range_factor()` is total
- **Date**: 2026-08-29
- **Status**: accepted
- **Context**: Testing Strategy **D4** proposed property-based tests over the calculation core. Scoping it required deciding what the invariants would assert, and that surfaced two behaviors in `utils/effective_sets.py` that no example test reaches.

  **First**, `calculate_effective_sets()` builds `muscle_contributions` as a plain dict keyed by muscle name (`utils/effective_sets.py:270-278`). When one muscle occupies two of the primary/secondary/tertiary slots, the later slot's assignment **overwrites** the earlier one, so the muscle is credited the *lower* weight rather than the combined weight. This is not hypothetical: **38 of the 1,897 exercise rows in the shipped `data/catalog.seed.db` repeat a muscle across the roles** — `Dumbbell Wrist Curl` (Forearms, Forearms, —), `Barbell Pronated Pendlay Row` (Latissimus Dorsi, Biceps, Biceps), `Kettlebell Farmers Carry` (Forearms, Forearms, Core) among them — and `utils/exercise_manager.py` applies no role-distinctness validation to user-added exercises, so 38 is a floor. Both summary aggregators then iterate the three-role tuple and re-read the collided key (`utils/weekly_summary.py:104-137`, `utils/session_summary.py:115-142`), so on `Dumbbell Wrist Curl` at 3 sets / RIR 0 / 8–12 reps the **Effective** column reports **3.0** where the **Raw** column reports **4.5** — a 33% understatement, on the same screen, with no indication which is right. Three facts settle the direction: the Raw column already sums the role weights; `utils/_fatigue/per_muscle.py:183-206` already accumulates the identical input correctly with `totals.get(bucket, 0.0) + …`, so two calculation modules in this repository disagree on the same catalog row; and the module docstring describes weighting by role, not by name. Taking the max would leave Raw and Effective permanently inconsistent and would leave the fatigue module an outlier.

  **Second**, `get_rep_range_factor()` keys its buckets on *disjoint closed intervals* — `(1,5)`, `(6,12)`, `(13,20)`, `(21,30)`, `(31,100)` — and computes a representative as `(min + max) / 2.0`. A fractional or out-of-range average therefore matches no bucket and falls through to `DEFAULT_MULTIPLIER = 1.0`. Measured fall-throughs: `(5,6)` → 1.0, `(20,21)` → 1.0, `(30,31)` → **1.0**, `(150,150)` → 1.0. The `(30,31)` case is the decisive one: 1.0 sits **above both** neighbours (0.85 at an average of 30, 0.70 at 31), which is a non-monotonicity rather than a defensible boundary choice. No rep upper bound exists anywhere — `utils/constants.py` bounds weight and RIR only, and `validate_workout_bounds()` checks `min <= max` and nothing else — so a 150-rep prescription persists and scores full hypertrophy credit. The correct shape is already in the repository: `utils/_fatigue/core.py:33-39` uses cumulative upper bounds terminating in `float("inf")`, which is total and monotone by construction. The suite's only property-shaped test, `test_never_returns_zero_factor`, samples reps `[3, 8, 15, 25, 40]` — every one inside a bucket — so it misses all four gaps by construction.
- **Decision**: **(1)** A muscle occupying more than one P/S/T role is credited the **sum** of the applicable role weights. Primary + secondary is therefore **1.5×** in `TOTAL` mode, matching Raw Sets and `utils/_fatigue/per_muscle.py`. **`DIRECT_ONLY` remains primary-only and is unchanged.** **(2)** `get_rep_range_factor()` is **total for valid positive rep averages**, on these bands: `avg < 6` → 0.85; `6 ≤ avg ≤ 20` → 1.0; `20 < avg ≤ 30` → 0.85; `avg > 30` → 0.70; missing rep data stays neutral at 1.0. So `(5,6)` → 0.85, `(20,21)` → 0.85, `(30,31)` → 0.70, `(150,150)` → 0.70. **No ingress rep validation is added or changed by this ADR** — that is separate scope, and this decision deliberately makes the calculation total instead of relying on validation to keep it in-domain.
- **Consequences**: Ruling (1) cannot be implemented inside `calculate_effective_sets()` alone. Because both aggregators re-read `muscle_contributions.get(muscle, 0.0)` once *per role*, an accumulated value would be added twice for a duplicated muscle, producing 3.0× where 1.5× is intended — strictly worse than the defect it replaces. The fix is therefore **atomic across `utils/effective_sets.py`, `utils/weekly_summary.py` and `utils/session_summary.py`**, deduplicating the role list into a per-muscle summed weight before the aggregation loop. That also moves `weekly_summary.py`'s `sessions_by_muscle[muscle][routine] += eff_contribution` accumulation, which feeds the `>= 1.0` frequency threshold, so frequency can change for a duplicate-muscle row: this is a user-visible calculation change requiring migration notes. Ruling (2) changes the factor for ordinary prescriptions — a 5–6 rep range moves from 1.0 to 0.85 — which is a deliberate accuracy correction, not a regression. Both are informational-only outputs: per the `utils/effective_sets.py` module docstring, effective sets never auto-adjust or block user intent, so no user action is gated on either number. `tests/goldens/weekly_summary_golden.json` is expected to be **byte-identical** after ruling (1), because every exercise its fixture seeds uses distinct P/S/T muscles; a diff there would mean the change reached further than intended and is a stop condition, not a regeneration prompt. The rulings are what make D4's two authorized packets assertable; the scope of that signature is `TESTING_STRATEGY_PLANNING.md` §8.1e and the execution plan is `testing_d4_invariants/PLANNING.md`.
